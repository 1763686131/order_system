# 权限角色分组优化方案

> 编写日期：2026-09-17  
> 适用范围：订单系统前端、后台管理端与 Flask/SQLite 后端  
> 目标：将当前“按账号保存权限数组”的方式，逐步调整为“用户加入角色组，角色组拥有权限与数据范围”的权限体系。

---

## 1. 当前现状

当前页面名为“角色管理”，但实际维护对象是登录账号：

- 新增时需要填写账号 ID、密码、名称和权限。
- 页面调用 `/api/users` 读取和保存用户。
- 权限以 JSON 数组保存到单个用户记录的 `permissions` 字段。
- `role` 字段目前主要是 `super_admin`、`admin`、`operator`、`employee` 四种固定等级。

这会带来以下问题：

1. 同岗位人员需要逐个勾选权限，容易出现权限不一致。
2. “管理员”“财务”“员工”等岗位无法形成可复用模板。
3. 权限 key 存在旧新命名混用，例如 `pending.view`、`pending.view_detail`、`shipped.receipt`、`shipped.view_receipt`。
4. 后台菜单、前端按钮、路由、后端接口没有使用同一份权限目录。
5. 部分权限只影响前端按钮显示，后端接口没有统一拦截。
6. 当前后端会信任浏览器传来的 `Role` 请求头，不能作为可靠的权限边界。
7. 用户列表接口会返回密码字段，登录密码当前也是明文保存和比对，存在严重安全风险。
8. 用户更新会通过全量删除再重写用户表的方式完成，不利于保留创建时间、状态、角色关联和审计记录。

因此，建议不继续在“每个账号单独勾选大量权限”的模式上扩展，而是先建立角色组。

---

## 2. 优化后的使用方式

权限关系调整为：

```text
员工档案 -> 关联登录账号
员工档案 -> 绑定角色组 -> 获得角色组权限
员工档案 -> 受门店/仓库/本人数据范围限制
```

示例：

```text
张三
  -> 员工档案：工号、姓名、头像、手机号、在职状态
  -> 登录账号：zhangsan
  -> 角色组：触屏员工
  -> 数据范围：门店 A、仓库 1
  -> 可录入原材料出库草稿，只能查看授权范围内的数据

李四
  -> 角色组：财务人员
  -> 数据范围：全部门店
  -> 可查看应收、收款、对账；不能管理用户和系统设置

王五
  -> 角色组：系统管理员
  -> 可管理用户、角色、门店、仓库和系统设置
```

日常操作应变为：

1. 管理员先维护“财务人员”“触屏员工”等角色组。
2. 在员工花名册中建立员工档案。
3. 为员工开通登录账号，或关联已有账号。
4. 给员工选择角色组，并指定可访问的门店、仓库或“仅本人数据”范围。
5. 员工重新登录后，系统根据其角色组决定可见菜单、可操作按钮和接口访问权限。

员工姓名、头像、工号等资料只维护在员工档案中。角色组成员列表、账号管理列表、审核记录和后续人事页面均通过 `employee_id` 关联读取，不能在角色表或权限表中重复保存姓名和头像。

## 3. 推荐角色组

以下是适合当前订单、库存、财务、触屏出库业务的初始角色组。角色组不应简单按“能修改、能删除”划分，而应按岗位职责组合具体业务权限。

| 角色组 | 主要用途 | 建议权限范围 |
| --- | --- | --- |
| 超级管理员 | 系统维护和紧急处理 | 所有权限；账号数量应尽量少 |
| 系统管理员 | 系统基础资料维护 | 用户、角色、门店、仓库、系统设置、打印模板 |
| 销售人员 | 销售订单日常录入与跟进 | 客户、销售订单新增/查看/修改、物流录入 |
| 销售审核人员 | 销售审核与反审核 | 销售订单查看、审核、反审核、查看销售应收 |
| 仓库操作员 | 入库、出库和库存日常操作 | 库存查看、入库草稿、出库草稿、指定仓库数据 |
| 仓库审核人员 | 审核库存业务 | 入库审核、原材料出库审核、反审核、库存流水查看 |
| 财务人员 | 收款、对账、应收管理 | 应收欠款、收款单、银行账户、物流/快运对账 |
| 财务审核人员 | 财务审核和反审核 | 收款审核/反审核、销售入账审核/反审核、财务流水查看 |
| 触屏员工 | 前端触屏端作业 | 仅前端触屏端、原材料出库录入、本人或授权仓库草稿查询 |
| 只读查看员 | 查询和展示 | 指定页面和指定门店/仓库的只读权限 |

说明：

- `超级管理员` 不应作为普通日常账号使用。
- `系统管理员` 不等于“所有业务都能删除或审核”。
- 触屏员工默认不进入 `/admin` 后台。
- 一个账号初期建议只配置一个主角色组，降低使用复杂度。
- 后续若确实需要“财务兼系统管理员”等场景，再支持一个账号加入多个角色组。

## 4. 统一权限目录

权限 code 建议统一采用：

```text
业务域.资源.动作
```

例如：

```text
sales.order.read
sales.order.create
sales.order.update
sales.order.delete
sales.order.complete
sales.order.reopen

sales.logistics.read
sales.logistics.edit
sales.logistics.audit

sales.receipt.read
sales.receipt.upload
sales.receipt.delete

inventory.stock.read
inventory.inbound.create
inventory.inbound.update
inventory.inbound.audit
inventory.inbound.reverse_audit

inventory.material_outbound.create
inventory.material_outbound.read
inventory.material_outbound.update
inventory.material_outbound.audit
inventory.material_outbound.reverse_audit
inventory.material_outbound.cancel

finance.receivable.read
finance.payment.create
finance.payment.update
finance.payment.audit
finance.payment.reverse_audit
finance.reconciliation.read

system.user.manage
system.role.manage
system.store.manage
system.warehouse.manage
system.settings.manage
system.print_template.manage
```

规则：

1. 页面访问、数据查看、创建、编辑、删除、审核、反审核、导出、打印应使用不同权限。
2. 不再保留含义重叠或无法对应实际业务的旧权限 key。
3. 前端权限树、前端按钮、路由元信息、后端接口校验全部引用同一份权限目录。
4. 权限目录必须有中文名称、业务模块、风险等级和说明，避免只靠 code 理解含义。

## 5. 数据库调整建议

### 5.1 账号表 `users`

`users` 只负责登录认证和账号生命周期，不负责保存完整员工资料：

```text
id                 用户主键
username           登录账号，唯一
password_hash      密码哈希，不保存明文密码
employee_id        关联员工档案，可为空
status             active / disabled / locked
last_login_at      最后登录时间
permission_version 权限版本号，用于强制旧登录状态失效
created_at         创建时间
updated_at         修改时间
```

建议一个员工最多关联一个日常登录账号，但员工档案可以在没有账号的情况下提前建立。

```text
UNIQUE(users.employee_id)
```

如存在服务账号、设备账号等非人员账号，可以允许 `employee_id` 为空，并单独配置其角色。

### 5.2 员工档案表 `employees`

`employees` 是花名册和人事行政的人员主数据。工资、考勤、检测报告、审核记录等后续模块都应使用 `employee_id` 关联员工，而不是使用姓名或登录账号。

建议字段：

```text
id                 员工主键
employee_no        工号，唯一
legal_name         证件姓名
display_name       系统显示姓名
avatar_url         头像地址或文件路径
gender             性别
birthday           出生日期
phone              手机号
email              邮箱
current_address    现居住地址
registered_address 户籍地址
emergency_contact  紧急联系人
emergency_phone    紧急联系人电话
department_id      部门 ID
position_id        职位 ID
manager_id         直属上级员工 ID
employment_type    正式、试用、兼职、临时等
employment_status  待入职、试用、在职、停职、离职、退休
hire_date          入职日期
probation_end_date 转正日期或试用期结束日期
leave_date         离职日期
leave_reason       离职原因
remark             员工备注
created_at
updated_at
```

注意：

- 不建议只设置一个 `is_active` 或 `is_employed` 布尔字段，应使用状态加日期记录完整生命周期。
- 员工姓名可能重复或修改，所有关联必须使用 `employee_id`。
- 员工离职后保留档案和历史业务记录，只禁止登录和新业务操作。
- 身份证号、家庭住址、工资银行卡等属于敏感信息，建议单独存储并按权限脱敏。

### 5.3 员工敏感资料表 `employee_sensitive`

身份证、工资卡等敏感字段不建议和普通员工资料一起返回：

```text
employee_id
id_card_type
id_card_no_encrypted
id_card_no_hash
bank_account_encrypted
tax_identifier_encrypted
created_at
updated_at
```

其中：

- 页面默认只显示身份证号后四位或掩码。
- `id_card_no_hash` 用于唯一性校验和查询，不能用可逆明文代替。
- 完整身份证号、银行卡号只对具备人事或工资权限的人员开放。
- 账号管理列表只返回必要字段，不返回全部敏感资料。

### 5.4 角色表 `roles`

```text
id                 角色主键
code               角色编码，例如 finance_staff
name               角色名称，例如 财务人员
description        角色说明
is_system          是否系统内置角色
status             active / disabled
created_at
updated_at
```

系统内置角色不允许随意删除；可以停用，但需要确保没有仍在使用的账号。

### 5.5 员工角色关联表 `employee_roles`

角色组从业务上绑定到员工，而不是绑定到姓名：

```text
employee_id        员工 ID
role_id            角色组 ID
is_primary         是否主角色
effective_from     生效时间
effective_to       失效时间
created_by         操作人
created_at
```

建议：

- 一个员工可以加入多个角色组，权限默认采用合并结果。
- 初期界面可以只展示一个主角色组，避免普通管理员配置复杂。
- 需要“财务兼系统管理员”时，再允许增加第二个角色组。
- 角色变更应保留生效和失效时间，支持调岗和历史追踪。
- 数据库增加 `UNIQUE(employee_id, role_id)`，避免重复绑定。

登录鉴权时通过以下关系计算权限：

```text
users.employee_id
  -> employees.id
  -> employee_roles.role_id
  -> role_permissions.permission_id
  -> permissions.code
```

如果未来同一员工需要多个账号且账号权限不同，可以补充 `user_roles` 作为账号级覆盖关系；在当前“一人一个账号”的场景下，优先使用 `employee_roles` 保持人事身份稳定。

### 5.6 权限表 `permissions`

```text
id                 权限主键
code               唯一权限 code，例如 finance.payment.audit
name               中文名称
module             所属模块，例如 finance
action             动作，例如 audit
description        权限说明
risk_level         low / medium / high
```

### 5.7 其他关联表

```text
role_permissions
  role_id
  permission_id

user_store_scopes
  employee_id
  store_id

user_warehouse_scopes
  employee_id
  warehouse_id
```

如需“只能看自己创建的数据”，可增加用户数据范围字段：

```text
data_scope
  all       查看全部授权门店/仓库数据
  assigned  仅查看已分配门店或仓库的数据
  own       仅查看本人创建的数据
```

不建议将门店、仓库范围继续塞进权限 JSON；它们属于员工的数据范围，不属于“财务人员”或“仓库操作员”这一岗位本身。

### 5.8 人事扩展表

为后续花名册、工资和考勤预留独立表，不要把会变化的工资和考勤字段直接塞进 `employees`：

```text
departments
  id
  name
  parent_id
  status

positions
  id
  name
  department_id
  status

employee_department_history
  employee_id
  department_id
  position_id
  effective_from
  effective_to

employee_salary_contracts
  employee_id
  effective_date
  base_salary
  position_allowance
  attendance_allowance
  status

attendance_records
  employee_id
  attendance_date
  clock_in
  clock_out
  attendance_status
  overtime_hours
  leave_hours
  source

employee_documents
  employee_id
  document_type
  file_id
  document_date
  visibility
```

现有 `hr_reports` 文件表后续应增加 `employee_id` 和 `document_type`，使检测报告、劳动合同等资料能直接关联员工档案，而不是只依赖文件夹路径。

### 5.9 审计日志表

高风险动作必须记录日志：

```text
audit_logs
  id
  actor_user_id
  actor_employee_id
  actor_name_snapshot
  action
  resource_type
  resource_id
  before_data
  after_data
  ip_address
  created_at
```

至少记录：

- 创建、修改、停用用户。
- 调整角色组和权限。
- 重置密码。
- 删除业务数据。
- 审核、反审核。
- 门店、仓库、系统设置变更。

## 6. 前端调整建议

### 6.1 页面拆分

当前“角色管理”建议拆为两个概念明确的页面：

| 页面 | 作用 |
| --- | --- |
| 账号管理 | 以员工花名册为主列表，维护员工资料、账号、角色组和门店/仓库范围 |
| 角色组管理 | 创建角色组、配置角色组权限、查看角色组成员的姓名、头像和在职状态 |

### 6.2 账号管理组件

账号管理建议使用员工档案作为列表主体，而不是直接把 `users` 表当作员工列表：

- 员工无账号时显示“未开通”。
- 员工有账号时显示登录账号和账号状态。
- 员工离职时保留档案，但默认禁止登录。
- 员工姓名、头像、工号从 `employees` 读取。
- 角色组从 `employee_roles` 读取。
- 身份证、住址、工资等敏感信息根据权限分区显示。

编辑抽屉建议分为：

1. 基本资料：工号、证件姓名、显示姓名、头像、性别、出生日期。
2. 联系方式：手机号、邮箱、现居住地址、户籍地址、紧急联系人。
3. 工作信息：部门、职位、直属上级、用工类型、入职/转正/离职日期、在职状态。
4. 账号安全：登录账号、账号状态、重置密码、最后登录时间。
5. 角色与范围：角色组、门店范围、仓库范围、本人数据范围。
6. 员工文件：身份证附件、合同、检测报告等，后续接入。

### 6.3 角色组管理组件

角色组管理只维护权限模板：

- 角色组名称、编码、说明和启用状态。
- 按业务模块配置查看、新增、修改、删除、审核、反审核等权限。
- 显示组内员工数量。
- 成员列表通过关联 `employees` 显示姓名、头像、工号、部门和在职状态。
- 不在 `roles` 表复制员工姓名、头像或联系方式。
- 可从角色组详情中添加或移除员工，实际写入 `employee_roles`。

角色组页面默认只展示成员必要信息，身份证、家庭住址、工资等资料应由人事专属页面或敏感权限控制。

角色组管理页不应出现账号密码输入框；账号管理页也不应让管理员重复勾选一大批岗位权限，只需要选择角色组。

### 6.4 菜单与路由

每个后台菜单和路由配置一个页面访问权限，例如：

```text
/admin/finance/payment-history
  -> finance.payment.read

/admin/roles
  -> system.role.manage

/admin/settings
  -> system.settings.manage
```

前端应做到：

1. 无权限菜单不显示。
2. 无权限直接输入 URL 时，路由跳转至无权限页面。
3. 页面内按钮按动作权限显示或禁用。
4. 修改角色后，目标账号下一次刷新或重新登录即可获取新权限。

注意：前端隐藏菜单和按钮只是体验优化，不是安全措施。

### 6.5 触屏端

触屏员工角色应具备独立体验：

1. 登录后默认进入 `/main`，不显示后台入口。
2. 仅显示可使用的标签页，例如原材料出库。
3. 不返回无权限模块的完整订单、客户、电话、地址、身份证和工资数据。
4. 只能提交草稿，是否可以审核由“仓库审核人员”单独控制。
5. 查询条件始终受门店、仓库和本人数据范围限制。

## 7. 后端鉴权调整建议

### 7.1 不再信任浏览器传入的 Role

当前 `Username`、`Role` 请求头属于客户端可修改数据，不能决定权限。

建议登录成功后：

1. 后端验证账号与密码哈希。
2. 后端签发服务端 session 或签名 token。
3. 每次请求由后端从 session/token 识别用户。
4. 后端查询该用户的角色组、权限和数据范围。
5. 后端决定是否允许访问接口，不以浏览器传来的 `Role` 为准。

### 7.2 统一接口守卫

后端应提供统一的鉴权能力，例如：

```text
require_login()
require_permission("finance.payment.audit")
require_store_scope(store_id)
require_warehouse_scope(warehouse_id)
```

接口处理顺序建议为：

```text
登录状态检查
  -> 权限检查
  -> 门店/仓库/本人数据范围检查
  -> 参数校验
  -> 执行业务操作
  -> 写审计日志
```

重点接口必须优先接入后端鉴权：

1. 用户、角色、密码、系统设置。
2. 删除订单、删除回单、删除单据。
3. 审核、反审核、库存过账、财务入账。
4. 创建和修改销售订单、收款单、入出库单。
5. 打印模板、路径设置、文件上传下载。

### 7.3 密码和用户资料安全

必须调整：

1. 数据库只保存 `password_hash`，不保存明文密码。
2. 用户列表接口不返回密码或密码哈希。
3. 管理员只能发起“重置密码”，不能读取旧密码。
4. 可增加首次登录强制修改密码。
5. 账号删除改为“停用”，保留审计和业务关联。
6. 角色或权限变化后，提高 `permission_version` 并让旧 session/token 失效。

## 8. 分阶段实施步骤

### 第一阶段：梳理与止损

目标：不改变主要业务流程，先消除明显安全风险和权限混乱。

1. 盘点所有现有权限 key、菜单、页面按钮和接口。
2. 建立唯一权限目录，标记“保留、重命名、废弃、未实现”。
3. 停止用户列表返回密码字段。
4. 密码迁移为哈希保存，并提供兼容旧密码的一次性升级方案。
5. 为用户、角色、系统设置和高风险业务接口增加登录校验。
6. 前端不再将 `Role` 作为可信身份传给后端。
7. 将当前角色页面临时改名为“账号与权限管理”，避免概念误导。

验收标准：

- 未登录用户不能读取用户列表和业务数据。
- 普通用户不能通过修改浏览器本地数据获得管理员接口权限。
- 任何接口响应中不出现密码明文或密码哈希。

### 第二阶段：建立角色组模型

目标：让“给一个人拉进组里”成为标准操作。

1. 创建 `roles`、`permissions`、`role_permissions`、`employee_roles` 表；`user_roles` 仅作为未来多账号场景的可选扩展。
2. 初始化本方案中的推荐角色组。
3. 创建 `employees`，将现有用户转换为员工档案。
4. 将 `users.employee_id` 关联到对应员工。
5. 将当前 `users.permissions` JSON 映射到角色组权限。
6. 将现有账号分配到一个默认角色组。
7. 保留旧 `role`、`permissions` 字段一段时间，仅用于迁移兼容。
8. 增加账号状态、创建时间、最后登录时间等生命周期字段。

验收标准：

- 新账号无需逐项勾选权限，只需选择角色组。
- 修改“财务人员”角色组后，组内账号自动获得相同权限。
- 内置角色不能被误删。

### 第三阶段：菜单、路由、按钮和接口统一

目标：同一个权限 code 在前后端拥有一致含义。

1. 为每个页面配置访问权限。
2. 为每个业务按钮配置动作权限。
3. 为每个 API 配置相同的后端权限守卫。
4. 对列表、详情、导出接口增加数据范围过滤。
5. 删除前端和文档中的废弃权限 key。
6. 建立角色权限矩阵测试用例。

验收标准：

- 没有页面只靠前端隐藏按钮来保护高风险操作。
- 无权限用户即使直接调用 API 也得到 `403`。
- 无权限用户不能通过直接输入 URL 进入后台页面。

### 第四阶段：数据范围与审计

目标：保证不同门店、仓库和岗位之间的数据隔离可追踪。

1. 给账号分配门店、仓库和本人数据范围。
2. 后端列表、详情、导出、打印接口统一按范围过滤。
3. 对审核、删除、权限变更等动作写审计日志。
4. 增加账号停用、会话失效和权限变更即时生效机制。

验收标准：

- 仓库操作员只能操作被分配的仓库。
- 触屏员工不能读取财务、客户隐私和系统管理数据。
- 可以追溯“谁在什么时间修改、删除或审核了什么数据”。

## 9. 迁移策略

为避免一次性改动过大，建议采用兼容迁移：

1. 先备份 SQLite 数据库和现有用户权限 JSON。
2. 导出当前用户列表，人工确认每个账号应归属的角色组。
3. 新建角色表和关联表，不立即删除旧字段。
4. 编写一次性迁移脚本，将旧权限数组映射为新的权限 code 或角色组。
5. 迁移后使用测试账号逐个验证菜单、按钮、接口和数据范围。
6. 观察稳定后，再停止读取旧 `users.permissions` 与旧 `users.role`。
7. 最后删除废弃权限 key、旧接口兼容逻辑和重复前端判断。

迁移期间建议始终保留一个经过验证的超级管理员账号，避免配置错误后无人可以恢复权限。

## 11. 本次优先级建议

| 优先级 | 工作项 | 原因 |
| --- | --- | --- |
| P0 | 密码哈希、用户列表脱敏、服务端身份认证 | 解决密码泄露与伪造角色风险 |
| P0 | 高风险接口统一后端鉴权 | 防止删除、审核、设置等越权操作 |
| P1 | 建立角色组、权限表和用户角色关联 | 实现“把人拉进组”的核心需求 |
| P1 | 菜单、路由、按钮按统一权限目录控制 | 让权限配置在界面上真正生效 |
| P2 | 门店、仓库、本人数据范围 | 满足多人、多门店、多仓库隔离 |
| P2 | 审计日志、账号停用、权限即时失效 | 提升可追溯性和长期维护能力 |

## 12. 最终建议

本系统下一步不应继续增加单账号权限勾选项，而应优先完成以下三件事：

1. 用后端可信登录身份替代浏览器传入的角色信息。
2. 建立“员工档案 -> 角色组 -> 权限”的统一模型。
3. 将登录账号关联员工档案，再通过员工绑定角色组。
4. 单独配置员工的门店、仓库和本人数据范围。

完成后，管理员只需要维护岗位模板；新增员工时先建立员工档案，再关联登录账号、角色组和数据范围。姓名、头像、工号等信息统一来自花名册，工资、考勤和人事资料继续使用 `employee_id` 关联，避免后续重复建档和数据不一致。
