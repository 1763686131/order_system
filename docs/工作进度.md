## 已完成

- 新增 `chat_conversations`、`chat_messages`、`chat_attachments`、`peer_file_transfers`、
  `notifications` 表和索引。
- 留言发送人从服务端 Session 获取，不接受前端传入发送人身份。
- 使用 `clientMessageId` 支持文字消息幂等，减少网络重试导致的重复留言。
- 附件保存在 `uploads/chat-attachments/YYYY-MM/`，数据库只保存相对路径和元数据。
- 下载附件时校验当前员工必须是消息发送人或收件人。
- `MessageInbox.vue` 的留言和通知两种模式均已接入真实接口。
- `ChatWindow.vue` 保留拖动和本地位置记忆，并接入历史、发送、附件及自动刷新。
- 单据审核通知按角色权限匹配收件人，同一事件通过唯一键去重。
- 单据审核完成后，相关通知统一标记为 `handled`。
- 单据删除、作废会结束旧通知，反审核或重新启用会生成新的审核通知。
- 新增 `/api/admin/realtime/events` SSE 通道，推送留言、已读状态和审核通知变化信号。
- 后台多个消息组件共享一个 `EventSource`，收到信号后再通过原接口获取完整鉴权数据。
- SSE 断开时浏览器自动重连，同时保留 60 秒轮询，避免代理或旧浏览器不支持长连接时停止刷新。
- 在线联系人可发起 WebRTC 文件直传，接收方在后台任意页面都能收到同意/拒绝请求。
- 文件采用 32KB 分块并启用发送缓冲背压，支持双方进度、取消、拒绝、失败和完成状态。
- Chromium 安全环境优先使用 File System Access API 直接写入磁盘；其他浏览器回退到内存接收后下载。
- 直传完成只保存文件名、大小和完成记录，文件内容不上传服务器，Offer/Answer 随结束状态清空。

## 权限和业务规则

- 留言功能由 `admin.message.read`、`admin.message.send`、`admin.message.attachment` 控制。
- 现有后台角色升级时一次性获得留言权限，之后以角色组配置为准。
- 销售审核通知复用 `admin.sales.order.audit`。
- 采购入库、原材料出库、收款、退货分别使用独立审核权限；权限同时控制审核接口和通知接收。
- 超级管理员拥有全部权限；普通员工必须有后台访问能力和对应权限。
- 收件人必须绑定启用账号，员工状态必须是“在职”或“试用”。

## 存储与运维注意事项

- 备份数据库时应同时备份 `uploads/chat-attachments/`，否则附件记录仍在但物理文件会丢失。
- 不要为 `chat-attachments` 单独增加公开静态路由；下载必须经过 Session 和会话参与者校验。
- 当前附件允许任意文件类型，部署到不可信网络前应增加扩展名白名单、MIME/文件头检测和病毒扫描。
- 当前单文件限制为 10MB，Flask 会把上传内容读入内存校验，不适合直接提高到超大文件。
- 审核通知是用户快照：创建单据时按当时角色权限生成，之后修改角色不会追溯增删旧通知。
- SQLite 适合当前内网小团队规模；消息量明显增长后需要增加归档策略和定期备份验证。
- SSE 接口每秒检查当前用户的消息和通知摘要，适合当前小团队；连接规模扩大后应迁移到 Redis
  Pub/Sub、消息队列或数据库变更事件，避免每个连接独立查询 SQLite。
- Nginx 等反向代理必须关闭 SSE 响应缓冲并提高读取超时；接口已经返回
  `X-Accel-Buffering: no`，代理层仍应显式配置。
- 多进程部署可以正常使用当前实现，因为变化判断来自 SQLite，不依赖单个 Python 进程的内存队列。
- WebRTC 未配置公网 STUN/TURN，仅使用主机候选，适用于同一局域网；无线 AP 客户端隔离、终端防火墙
  或跨 VLAN 策略可能阻止浏览器建立点对点连接。
- 在线直传没有应用层大小上限，但并非物理无限。非安全上下文或不支持 File System Access API 的
  浏览器需要在内存中拼接完整文件，大文件能力取决于接收端可用内存。
- 建议用 HTTPS 或 `localhost` 运行以获得磁盘流式写入能力；通过普通局域网 IP 的 HTTP 页面通常只能
  使用内存接收降级方案。

## 已知限制

- SSE 变化检测周期约 1 秒；网络或代理阻断长连接时会退回 60 秒轮询，因此极端情况下仍有延迟。
- 没有消息撤回、编辑、搜索、删除、送达回执、正在输入和桌面通知。
- 历史消息界面当前读取最近 100 条，后端会话接口已预留 `beforeId` 分页能力。
- 服务器离线附件暂不提供上传进度；在线直传暂不支持断点续传、并行多文件、文件预览和跨网 TURN 中继。
- 通知点击后通过路由查询参数定位单据，各目标列表页面仍需逐步完善按 `documentId` 自动聚焦。
- 当前开发机没有可用 Python 解释器，后端运行与接口集成测试需要在 Docker/Python 环境执行。

## 后续优化顺序

1. 增加后端接口测试，覆盖越权下载、重复消息、10MB 边界、通知去重和 SSE 会话失效。
2. 增加消息分页加载、发送失败重试、服务器附件上传进度和桌面未读提醒。
3. 完善目标业务页面按通知参数定位、筛选并高亮待审核单据。
4. 增加附件类型策略、审计日志、生命周期清理和备份恢复检查。
5. 连接数或消息量增长后，引入 Redis Pub/Sub 或消息队列替代 SSE 内部的 SQLite 摘要轮询。
6. 根据实际网络测试决定是否增加断点续传、SHA-256 完整性校验和可选内网 TURN 服务。

## 第二阶段验收建议

- 两个账号在不同浏览器登录，新留言应在约 2 秒内出现且未读数准确。
- 将留言标记为已读后，发送方已打开的聊天窗口应自动刷新已读状态。
- 新审核通知和审核完成状态应自动刷新，无需重新打开面板。
- 断网恢复后 SSE 自动重连；重连及 60 秒兜底查询不得重复插入同一个 `clientMessageId`。
- 非会话成员访问附件下载地址必须失败。
- 审核通知点击后能直接定位对应单据，审核完成后所有审核人通知同步变为已处理。
- 数据库与附件目录恢复演练后，历史留言和附件均可正常访问。

## 第三阶段验收建议

- 两个账号使用同一局域网内的 Chrome 或 Edge 登录，发送方发起后接收方应在约 2 秒内看到请求。
- 接收方拒绝、发送方取消以及任一浏览器断开时，双方状态应正确结束且服务器不产生附件文件。
- 分别测试小于 10MB 和大于 10MB 文件，核对接收文件大小、内容以及双方进度最终为 100%。
- HTTPS 或 localhost 环境应先弹出保存位置并流式写盘；普通 HTTP 环境应完成内存接收和浏览器下载。
- 传输完成后聊天记录出现在线直传留痕，`uploads/chat-attachments/` 不新增对应文件。
- 跨 VLAN、开启无线客户端隔离或防火墙阻断时应进入失败状态，不应自动退回服务器上传大文件。
