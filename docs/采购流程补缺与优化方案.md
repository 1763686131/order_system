# 采购流程补缺与优化方案

> 编写日期：2026-10-06
> 文档状态：待业务确认，确认后再进入开发
> 范围：采购进度、采购退货、采购费用归属、供应商应付、供应商付款、供应商对账
> 原则：本方案只定义目标流程、组件和接口，不代表功能已经实现。

## 1. 目标

在现有采购订单和采购入库流程上，补齐采购退货、独立采购入库和供应商财务闭环，并将采购履约进度和付款进度分别展示、分别计算：

```text
采购申请 -> 采购审核 -> 分批采购入库 -> 入库审核 -> 采购履约完成
                                             |
                                             +-> 供应商应付 -> 供应商付款 -> 供应商对账
采购入库批次 -> 采购退货 -> 库存减少、应付冲减或形成供应商贷项

独立采购入库（无采购订单）
    -> 正常独立入库：不选择供应商，不生成应付
    -> 待补供应商例外：先审核库存，后由财务补录供应商并确认应付

员工采购/费用报销（独立财务或员工模块，第一阶段仅前端原型）
    -> 员工填写费用和附件
    -> 前端临时展示页面状态，不代表真实审核或付款
    -> 不进入采购订单、采购入库、库存或供应商应付
```

采购履约完成只表示采购数量已入库，不表示款项已经付清。付款完成只表示供应商账务已结清，不代表采购数量已经收齐。两者不得共用一个状态字段。

正常独立入库不选择供应商，也不生成供应商应付。只有因实际货物已经到库但采购订单尚未建立等特殊情况，才允许使用“待补供应商”例外；补录供应商后只进入供应商应付、付款和采购退货流程，不会自动生成采购订单，也不会产生采购订单的计划数量和采购履约进度。

## 2. 当前基础与缺口

### 2.1 已有能力

- 采购订单：申请、审核、反审核、订单详情和可入库明细，接口为 `/api/purchase-orders`。
- 采购入库：独立入库、关联采购订单入库、分批入库、批次日期、审核/反审核，接口为 `/api/stock-inbounds`。
- 采购订单明细按行关联供应商；同一采购订单可以有多个供应商。
- 采购入库可以包含原材料和成品，支持实际入库数量超过采购数量。
- 独立其他入库不要求供应商；当前可以作为无采购订单的实际入库入口，但还没有明确区分“无需结算”和“待补供应商”。
- 当前采购订单的付款金额、结算账户和本次付款字段只保存采购单数据，不产生供应商付款流水或银行账户流水。

### 2.2 尚未形成的能力

- 没有采购退货单及供应商退货接口；现有 `/api/returns` 是销售退货，处理客户应收和客户退款，不能直接充当采购退货接口。
- 没有供应商付款单、付款审核和供应商付款历史。
- 没有可靠的供应商应付流水来源。当前 `suppliers.payable` 不会随采购审核、入库审核和付款自动变化。
- 财务详情页的“应付”模式尚未接供应商数据，不能仅通过切换标题复用客户欠款接口。
- 没有供应商对账单及按期间核对期初、发生额、期末余额的能力。
- 独立入库没有结算归属字段，无法明确判断后续是否需要补录供应商并进入供应商应付。
- 没有“补录供应商并确认应付”的独立操作，不能安全地把已入库但未归属供应商的单据纳入账务。
- 没有独立的员工采购/费用报销前端模块；该模块不应通过原材料采购入库单实现。

相关现状可参阅 [API接口文档.md](./API接口文档.md) 的采购订单、供应商、入库和客户退货章节，以及 [README.md](../README.md) 的采购与财务路由说明。

## 3. 目标状态与进度定义

### 3.1 采购履约状态

采购履约状态来源于采购订单明细和已审核采购入库数量，不使用付款数据。

| 状态 | 规则 | 建议显示 |
| --- | --- | --- |
| `draft` | 采购申请草稿 | 草稿 |
| `pending` | 等待采购审核 | 待审核 |
| `approved` | 已审核，尚无有效入库数量 | 待入库 |
| `partial` | 至少一行有入库，但仍有明细未达到采购数量 | 部分入库 |
| `completed` | 所有采购明细累计实收数量大于或等于采购数量 | 已完成 |
| `cancelled` / `rejected` | 已取消或审核驳回 | 按现有状态展示 |

数量进度按每行计算：

```text
采购履约进度 = 已审核累计入库数量 / 采购数量
```

- 分母为采购数量，分子只累计已审核且未反审核的关联采购入库实收数量。
- 数量达到或超过采购数量时，显示为 `100%` 和“已完成”；超出的实际数量仍需原样展示，不丢弃、不截断库存。
- 已完成的明细不再显示“补充入库”；仍未达到采购数量的明细继续显示可补充入库数量。
- 采购订单含多行商品时，列表进度可显示“已入库数量 / 采购数量”，订单总进度以数量汇总计算；不同单位混合时不直接相加，应显示“已完成行数 / 总行数”或分行进度。
- 采购退货不回减历史累计入库数量，这是已确认的业务规则。采购订单继续保留原累计入库数量和原采购履约状态，同时单独显示退货数量、退货金额和净库存影响。
- 采购订单完成入库后发生退货，不重新打开原采购订单的补充入库入口；如需补回数量，应新建采购订单或独立采购入库。

### 3.2 付款状态

付款状态根据已入账供应商应付和已审核付款/贷项计算，不读取采购订单的“预计付款”字段。

| 状态 | 规则 | 建议显示 |
| --- | --- | --- |
| `unpaid` | 当前应付大于 0，已付款为 0 | 未付款 |
| `partial` | 当前应付大于 0，且已有部分付款 | 部分付款 |
| `paid` | 当前应付为 0，且没有待核销的预付款或贷项 | 已结清 |

付款状态只表示应付是否已经通过付款单结清；供应商预付款和供应商贷项不自动冲销应付，另以独立余额和“有可用供应商余额”标记展示。

建议列表按供应商或采购订单显示以下数字，而不是只显示一个含义不明的“付款进度”：

```text
已确认应付、已付款/已核销、未付应付、供应商预付款、供应商贷项
```

只有当应付和付款可明确归属某一采购订单时，才显示订单级付款百分比。未分配付款应计入供应商预付款，但不应伪装成某张采购订单的已付款。预付款和退货形成的供应商贷项必须分开记录、分开核销、分开展示。

供应商付款单是实际付款的唯一入口，使用方式对齐客户侧收款单：先保存付款草稿，再选择供应商应付进行核销，最后审核入账。采购订单中的 `currentPayment` 只作为历史采购字段保留，不参与供应商付款状态计算。

### 3.3 开票状态

开票状态独立于采购履约状态、应付状态和付款状态。是否已开票不决定是否已经产生应付，只记录供应商发票的接收、登记和核对情况。

| 状态 | 规则 | 建议显示 |
| --- | --- | --- |
| `not_required` | 无需供应商发票的业务 | 不需要发票 |
| `unbilled` | 已产生应付，但暂未登记供应商发票 | 未开票 |
| `partial` | 只登记了部分商品、数量或金额的发票 | 部分开票 |
| `billed` | 关联应付金额已全部登记发票 | 已开票 |
| `difference` | 发票金额、数量或税额与应付存在差异，等待处理 | 开票有差异 |

建议在采购订单和供应商对账单中同时展示：

```text
已确认应付、已开票金额、未开票金额、已付款、未付款
```

- 采购订单列表显示汇总开票状态；采购订单详情按商品明细或入库批次显示开票状态。
- 供应商对账单按账务流水显示开票状态，并支持筛选“未开票/部分开票”。
- 不能只在采购订单表头保存一个布尔值，因为一张发票可能对应多张入库单，一张采购订单也可能分多张发票开具。
- 数量单位不一致时，以金额作为开票进度主要依据，同时保留开票数量和税额。

## 4. 建议的入账规则

### 4.1 采购订单审核

- 采购订单审核表示采购承诺生效，不直接增加供应商应付，不扣减银行余额。
- 采购订单中现有的 `paymentAmount`、`currentPayment`、`settlementAccount` 不能再作为真实付款依据。
- 建议将订单金额保留为采购估算/合同金额；实际付款必须通过独立的供应商付款单。
- 确认本方案后，可在新流程中停用或移除订单上的“本次付款”输入，避免同一笔付款被重复记账。

### 4.2 采购入库审核与应付确认

**建议第一阶段以采购入库审核作为应付确认时点**，规则如下：

- 关联采购订单的入库，沿用采购订单明细供应商；只有供应商明确的入库行才生成供应商应付。
- 草稿保存不产生库存变更和应付流水；入库审核在同一事务中完成库存过账、采购累计入库更新和应付流水写入。
- 采购订单可以包含多个供应商；入库明细必须保留对应采购明细的供应商，按供应商和入库明细分别生成应付来源，不能只在入库单头保存一个供应商或一条应付流水。
- 应付按本批实际入库数量、审核确认的采购单价及税额快照计算；含税金额、未税金额和税额必须分别保存，费用必须先完成明确归属后才能计入应付。
- 采购订单尚未入库的数量不计应付。
- 超量入库按实际审核数量确认应付，不以采购数量封顶。
- 反审核须同时撤销对应库存流水和应付流水；如果该应付已被付款、退货或对账确认引用，应阻止反审核并提示先处理后续单据。

入库审核后，该供应商应付默认开票状态为 `unbilled`。未开票不影响应付余额，但是否允许付款由财务规则控制。

### 4.2.1 开票状态与后续发票登记

第一阶段只记录和展示开票状态，不开发完整的发票分配闭环：

1. 采购入库审核时生成供应商应付，开票状态初始化为 `unbilled`。
2. 采购订单详情和供应商对账单可以人工维护或展示“已开票/未开票”状态、开票备注和已开票金额。
3. 第一阶段不允许通过发票登记改变应付本金、库存数量或银行余额。
4. 第二阶段再增加发票登记，将发票分配到一张或多张采购订单、入库批次或应付明细。
5. 完整发票登记时，同一张发票可以分配多个入库批次，同一入库批次也可以分多张发票登记。
6. 发票登记金额超过应付、发票供应商与应付供应商不一致，或税额明显不一致时，标记为“开票有差异”，不能静默覆盖原采购价格。
7. 如果以后要求“收到发票才确认应付”，应增加发票驱动的应付确认模式，但不建议与入库驱动模式同时对同一业务重复入账。

建议增加系统配置：

```text
paymentRequireInvoice = false
```

付款模块启用后默认允许未开票付款，但付款单必须填写“未开票付款原因”，并保留付款人和审核人。后续如果财务要求见票付款，再将配置改为 `true`；开启后，供应商付款审核只允许选择已开票或财务明确豁免的应付。

### 4.2.2 独立采购入库的结算归属

独立采购入库继续使用现有 `/api/stock-inbounds`，不新增另一套库存入库接口。正常独立入库不选择供应商；只有已经实际到货但暂时无法关联采购订单的特殊情况，才使用“待补供应商”结算归属。

| 结算归属 | 供应商要求 | 库存审核 | 应付处理 | 后续入口 |
| --- | --- | --- | --- | --- |
| `none` 无供应商独立入库 | 不允许选择供应商 | 正常增加库存 | 不生成供应商应付 | 仅作为实际库存入库记录 |
| `pending_supplier` 待补供应商 | 新建时不填写供应商 | 允许先审核库存 | 不生成应付 | 财务补录供应商并确认应付 |

建议操作规则：

1. 新增独立入库时，结算归属默认为 `none`；如果确认货物属于尚未建立采购订单的供应商采购，只能选择 `pending_supplier`，不能直接选择供应商。
2. 草稿状态下可以在 `none` 与 `pending_supplier` 之间切换，但只要填写了供应商，就必须改走采购订单关联入库。
3. `none` 入库审核只写入库存，不生成应付；单据显示“已入库/无需结算”。
4. `pending_supplier` 入库审核只写入库存，单据显示“已入库/待补供应商”，不能显示为“已完成付款”或“无需付款”。
5. 已审核的待补供应商单据不能通过普通编辑修改财务归属。应使用“补录供应商并确认应付”流程，由有财务权限的人员按入库明细补录供应商后确认应付，记录操作人和时间。
6. 补录供应商后，单据仍是独立采购入库，不会自动转成采购订单；它可以进入供应商付款和采购退货，但没有采购计划数量，也不参与采购订单履约进度。
7. 待补供应商入库允许按明细补录多个供应商；每条明细只能归属一个供应商，每个供应商分别生成应付来源。
8. 员工垫付、办公用品、五金和零星费用不通过独立采购入库处理，直接进入独立员工采购/费用报销前端原型。
9. `pending_supplier` 可以先审核库存，但不能长期存在。列表增加“待补供应商”筛选，并持续提示后续必须补录供应商。

这里的“后补供应商”是财务归属补录，不是把独立入库伪装成普通采购订单。普通采购订单仍然负责采购计划和采购履约进度；独立采购入库只负责实际到货和库存，只有补录确认后才进入供应商应付。

### 4.2.3 采购费用和报销费用

- 采购订单“其它费用”第一阶段不做按数量或金额自动分摊。
- 如果费用属于供应商采购，应明确归属某个供应商和某条采购/入库商品明细；分批入库时只在对应批次确认实际发生的费用。
- 费用不能只保存在采购订单表头。建议建立采购费用明细，至少包含 `expenseType`、`supplierId`、`purchaseOrderItemId`、`inboundItemId`、`amountExcludingTax`、`taxAmount`、`amountIncludingTax`、`includeInPayable`、`includeInInventoryCost` 和 `remark`。
- 未明确供应商或商品明细归属的费用只能作为备注或估算金额，不能进入供应商应付，也不能进入库存成本；采购入库审核或应付确认时应阻止提交。
- 员工垫付、办公用品、五金、零星采购和没有库存的费用，全部进入独立员工采购/费用报销模块，不进入供应商应付。
- 报销模块第一阶段只做前端原型和交互，不调用采购订单、采购入库、库存或供应商账务接口；页面数据只保留在当前页面临时状态，不作为正式业务数据。
- 报销页面可以临时录入费用类型、金额、商户名称、报销人、付款方式、备注和发票/收据附件，但不展示真实的审核、付款和财务余额。
- 后续如需正式报销审核和付款，再单独设计员工报销后端接口，不与原材料采购流程合并。

### 4.3 采购退货审核

- 采购退货必须关联原采购入库商品行/批次，记录供应商、商品类型、仓库、批次、退货数量和退货金额。
- 可退数量不得超过原入库已审核数量减去此前有效退货数量；库存也必须足够扣减。
- 审核时在一个事务内扣减库存，并生成供应商退货/贷项流水。
- 尚未付款的部分冲减应付；已付款的部分形成独立供应商贷项，不直接产生含义不清的负应付。
- 允许录入供应商实际确认的退货金额，不强制等于原入库价格快照。
- 库存退货成本仍按原入库单的单价和税额快照处理，确保库存成本和库存流水可追溯。
- 供应商应付冲减金额按供应商实际确认的退货金额处理；与原入库成本的差额单独记录为采购退货价格调整。
- 采购退货审核不回写采购订单的累计入库数量，也不改变原采购订单的 `approved`、`partial` 或 `completed` 履约状态。
- 退货价格调整必须填写差异原因、确认人和确认时间，不能直接覆盖原采购入库价格。
- 如果供应商确认金额包含不同税率、折扣或额外补偿，应按金额和税额分别记录，不能只修改一个含税总额。
- 退货草稿不影响库存和应付；反审核恢复相应流水，已被付款或对账确认引用时需先解除后续引用。
- 采购退货单独产生供应商贷项，不直接处理供应商银行退款；实际退款通过独立的供应商退款单登记，并由退款审核/反审核分别写入或冲销银行流水。

### 4.4 供应商付款审核

供应商付款单采用与客户收款单一致的“保存草稿、选择应付、核销审核”模式：

1. 付款单必须关联一个供应商、门店、结算账户、付款日期、金额和付款方式。
2. 新建或修改草稿时，按照供应商加载可核销的应付流水，显示来源单号、入库日期、应付金额、已核销金额、未核销金额、开票状态和本次核销金额。
3. 支持一次付款核销多条应付，也支持一条应付被多次部分付款核销。
4. 草稿阶段只保存付款信息和核销分配，不改变供应商应付、银行余额或付款状态。
5. 审核时重新读取供应商最新未核销余额，校验本次核销金额，避免多人同时操作导致超额核销。
6. 审核成功后，在同一事务内写入银行账户流水、供应商付款流水和付款核销关系，并更新来源应付的已核销金额。
7. 付款总额大于本次核销总额时，差额自动明确记录为供应商预付款，并与应付余额、供应商贷项分开显示，后续可单独核销。
8. 付款总额小于本次核销总额时，审核前直接拒绝，不能自动截断核销金额。
9. 若开启 `paymentRequireInvoice`，未开票应付不能参与核销，除非付款人拥有财务豁免权限并填写原因。
10. 已有供应商预付款或贷项的使用必须通过独立核销明细完成，不能直接修改余额；付款单只记录本次实际付款，预付款/贷项使用单独记录，不计入本次银行付款金额。
11. 反审核需要同时恢复银行余额、供应商付款流水和应付核销金额；已经参与对账确认、退货或后续付款的付款单，必须先解除关联。

付款单不是采购入库单，也不改变采购履约数量；它只负责资金流出和供应商应付核销。

### 4.5 供应商期初余额

开发端不迁移现有 `suppliers.payable` 数据，也不读取或写入旧字段。直接启用新的供应商账务流水作为唯一余额来源。

如果新账务启用时确实存在需要录入的期初余额，只允许按新账务规则重新录入，并分别形成可追溯的 `INITIAL` 期初流水；这不是旧数据迁移。

## 6. 第三阶段接口设计与实现说明

本节保留采购流程的接口边界和业务约束。第三阶段接口已经落地，当前请求/响应字段、权限和错误码以《API接口文档》v5.13 的“采购模块第三阶段新增接口”为准；本节中的方法和命名用于说明业务模型。

### 6.1 采购退货

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/purchase-returns` | 查询采购退货列表，支持门店、供应商、日期、状态、单号筛选 |
| `GET` | `/api/purchase-returns/{id}` | 获取采购退货单及明细 |
| `GET` | `/api/stock-inbounds/{id}/returnable-items` | 查询该入库单仍可退的商品、批次和数量 |
| `POST` | `/api/purchase-returns` | 新建退货草稿 |
| `PUT` | `/api/purchase-returns/{id}` | 修改未审核草稿 |
| `DELETE` | `/api/purchase-returns/{id}` | 删除未审核草稿 |
| `POST` | `/api/purchase-returns/{id}/audit` | 审核退货，扣库存并记供应商贷项 |
| `POST` | `/api/purchase-returns/{id}/reverse-audit` | 反审核，撤销库存和供应商账务影响 |

建议退货明细至少包含 `inboundId`、`inboundItemId`、`purchaseOrderId`、`purchaseOrderItemId`、`supplierId`、`productType`、商品 ID/名称快照、仓库、批次、退货数量、单价快照、退货金额和备注。后端必须重新校验可退数量、供应商归属和库存，不依赖前端校验。

采购退货来源可以是采购订单入库，也可以是已经确认供应商归属的独立采购入库。只有完成供应商明细归属的独立入库明细才能创建采购退货单。待补供应商和无需结算的入库不能直接创建采购退货单。采购退货只形成供应商贷项，实际退款通过独立的供应商退款单处理；员工报销模块不属于采购退货范围。

### 6.2 独立采购入库与结算归属

现有 `/api/stock-inbounds` 保留，不新增办公采购专用库存接口。建议在请求和响应中增加以下字段：

| 字段 | 取值/说明 |
| --- | --- |
| `documentSource` | 继续使用 `purchase-order`、`other`、`production`；独立入库使用 `other` |
| `settlementType` | `none`、`pending_supplier`；不提供普通独立入库的 `supplier` 模式 |
| `supplierId` | 独立入库创建和审核时必须为空；补录供应商后只保存在入库明细归属中 |
| `supplierAssignmentStatus` | 入库明细级取值：`not_required`、`pending`、`confirmed` |
| `payableTransactionId` | 只允许保存在入库明细或应付来源关系中；一张入库单可能对应多个供应商和多条应付流水 |
| `supplierAssignedBy` / `supplierAssignedAt` | 记录补录供应商的操作人和时间 |
| `settlementRemark` | 结算归属、补录原因或财务备注 |

建议新增接口：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/stock-inbounds?businessType=purchase&settlementType=...` | 查询独立入库并按结算归属筛选 |
| `GET` | `/api/stock-inbounds/{id}/settlement` | 查询独立入库的结算状态、供应商和可确认金额 |
| `POST` | `/api/stock-inbounds/{id}/assign-supplier` | 按入库明细补录一个或多个供应商；不重复入库 |
| `POST` | `/api/stock-inbounds/{id}/confirm-payable` | 对已补录供应商的入库明细确认应付，按供应商分别生成账务流水 |

规则：

- 草稿独立入库直接通过现有 `PUT /api/stock-inbounds/{id}` 修改结算归属；独立入库请求携带 `supplierId` 时必须返回 `400`，要求改走采购订单流程。
- 已审核单据不允许用普通编辑修改财务归属；先调用 `assign-supplier`，再调用 `confirm-payable`。
- `assign-supplier` 的请求必须携带 `items: [{ inboundItemId, supplierId }]`，每条入库明细只能归属一个供应商。
- `confirm-payable` 必须幂等，同一入库明细和供应商只能生成一条有效的采购应付确认流水；重复提交返回当前确认结果。
- 供应商确认金额按入库明细的实际数量和价格快照计算；如果存在费用，必须明确费用归属后才能确认。
- 供应商补录和应付确认之间允许暂存，但必须显示“已补供应商/待确认应付”，不能提前计入供应商余额。
- 员工报销不通过采购入库关联，也不填写 `supplierId`，不生成供应商应付。

### 6.3.1 供应商采购费用归属（第一阶段）

采购费用第一阶段不做自动分摊，但供应商费用必须可以明确归属并进入应付或库存成本：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/purchase-orders/{id}/expenses` | 查询采购订单的费用明细和归属状态 |
| `POST` | `/api/purchase-orders/{id}/expenses` | 新增明确归属供应商/商品明细的费用草稿 |
| `PUT` | `/api/purchase-expenses/{id}` | 修改未确认费用归属 |
| `DELETE` | `/api/purchase-expenses/{id}` | 删除未确认费用 |
| `POST` | `/api/purchase-expenses/{id}/confirm` | 确认费用归属，允许后续入库应付使用 |

费用请求必须携带 `supplierId`、`purchaseOrderItemId` 或 `inboundItemId`、未税金额、税额、含税金额、是否进入应付、是否进入库存成本和备注。未明确归属的费用不能确认；后端必须校验供应商与商品明细一致，不能由前端自行拼接供应商账务。

### 6.4 采购发票登记（第二阶段）

第一阶段只保留采购订单和供应商对账中的开票状态、开票备注和汇总金额。第二阶段再单独建立采购发票登记接口。发票登记不等同于付款，也不重复生成应付。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/purchase-invoices` | 查询发票登记列表，支持供应商、日期、开票状态、单号筛选 |
| `GET` | `/api/purchase-invoices/{id}` | 获取发票详情及分配明细 |
| `POST` | `/api/purchase-invoices` | 新建发票登记草稿 |
| `PUT` | `/api/purchase-invoices/{id}` | 修改未确认发票登记 |
| `DELETE` | `/api/purchase-invoices/{id}` | 删除未确认发票登记 |
| `POST` | `/api/purchase-invoices/{id}/confirm` | 确认发票登记，更新来源应付的开票状态 |
| `POST` | `/api/purchase-invoices/{id}/reverse-confirm` | 撤销发票登记，恢复来源应付的开票状态 |

发票登记至少包含供应商、发票号码、发票日期、发票类型、发票金额、税额、价税合计、附件和备注。分配明细至少包含来源采购订单、入库批次或供应商应付流水 ID，以及本次分配金额、数量和税额。

接口校验要求：

- 发票供应商必须与被分配的采购应付供应商一致。
- 一张发票可以分配多条应付；一条应付也可以被多张发票部分覆盖。
- 已分配发票金额不能超过可开票应付金额；超出部分必须明确登记为差异或不允许确认。
- 发票确认不能改变库存数量、采购履约数量、供应商应付本金或银行余额。
- 发票撤销不能影响已经发生的付款，只能在没有后续锁定或财务调整引用时执行。

如果第一阶段暂不开发完整发票列表，也至少应在采购订单详情和供应商对账单增加开票状态、已开票金额、未开票金额和发票备注字段；后续补登记接口时不得改变既有应付数据。

| `GET` | `/api/suppliers/{id}/balance` | 获取指定供应商应付、预付款、贷项和净额摘要 |
| `GET` | `/api/suppliers/{id}/credits/allocatable` | 获取指定供应商可核销的贷项 |
| `POST` | `/api/suppliers/{id}/credits/{creditId}/allocate` | 将供应商贷项核销到指定应付来源 |

对账明细建议统一返回期初、采购入账、采购退货、付款、预付款、贷项、调整、反审核/冲销记录及期末余额。每一行需包含业务日期、审核时间、单号、业务类型、增加/减少金额、余额、来源单据 ID、来源明细 ID 和审核状态。接口必须明确日期范围按业务日期筛选，期初取开始日期前最后一笔有效余额。

付款草稿请求应包括供应商、门店、业务日期、付款日期、银行账户、付款方式、付款总额、分配到的应付来源及金额、未分配预付款金额、未开票付款原因、附件和备注。分配明细合计不得超过付款总额；付款总额与分配金额的差额必须明确成为供应商预付款，不能丢弃。已有预付款或贷项的使用不应伪装成新的银行付款，必须通过独立核销关系记录。

付款审核请求应携带核销明细，后端必须重新校验：

- 核销明细中的应付流水属于当前供应商，且状态有效。
- 本次核销金额大于 0，不能超过该应付的未核销金额。
- 本次银行付款金额 = 本次新增应付核销金额 + 本次新增预付款金额；已有预付款或贷项的使用金额单独记录，不计入本次银行付款金额。
- 同一付款单只能生成一条有效付款流水；重复审核必须返回当前状态，不得重复扣减银行余额。
- 付款单的审核状态与应付核销状态分别保存，方便对账和反审核。

### 6.8 共通接口约束

所有新增采购财务接口都必须返回当前单据状态、业务日期、审核时间、操作人、版本号和来源单据摘要，不能只返回“操作成功”。

建议统一状态：

| 单据/业务 | 状态 |
| --- | --- |
| 采购退货 | `draft`、`pending`、`audited`、`reversed`、`cancelled` |
| 供应商付款 | `draft`、`pending`、`audited`、`reversed`、`cancelled` |
| 采购发票 | `draft`、`confirmed`、`reversed`、`cancelled` |
| 待补供应商结算 | `pending_supplier`、`supplier_assigned`、`payable_confirmed` |

通用校验要求：

- `400` 表示请求字段、金额或明细格式错误；`404` 表示来源单据不存在；`409` 表示状态冲突、并发修改或余额已被其他单据占用。
- 每个审核、反审核、补录供应商和核销请求都必须支持幂等键；重复提交返回当前结果，不得重复写入库存、银行或供应商账务。
- 金额统一使用定点小数保存，至少分别保存未税金额、税额和含税金额；后端按明细计算并在单据级汇总，不能依赖前端传入总额。
- `businessDate` 用于账务期间和对账筛选，`createdAt`、`auditedAt`、`reversedAt` 用于操作追溯，不能用同一个时间字段代替。
- 来源账务必须保存 `sourceType`、`sourceId`、`sourceItemId`、`supplierId` 和 `storeId`；反审核使用冲销流水，不直接删除已入账记录。

## 7. 数据与账务模型建议

新账务以不可覆盖的供应商账务流水作为余额依据，不读取或写入旧 `suppliers.payable` 数据。第一阶段不保留旧字段兼容逻辑；供应商余额全部由新账务流水汇总。

| 数据实体 | 主要内容 |
| --- | --- |
| `supplier_account_transactions` | 供应商 ID、门店、业务日期、审核时间、业务类型、来源类型/来源 ID/来源明细 ID、未税金额、税额、含税金额、应付增加/减少、预付款增加/使用、贷项增加/使用、状态、冲销关联和幂等键 |
| `purchase_returns` / `purchase_return_items` | 采购退货单头、来源入库行、商品/供应商/仓库/批次快照、退货数量、原入库价格快照、供应商确认金额、差异金额/原因和审核状态 |
| `supplier_payments` / `supplier_payment_allocations` | 付款单头、结算账户、付款金额、付款状态、未开票付款原因，以及付款到应付来源、预付款和贷项的核销关系 |
| `purchase_expense_lines` | 费用类型、供应商、采购订单明细、入库明细、未税金额、税额、含税金额、是否进入应付、是否进入库存成本、归属状态和备注 |
| `stock_inbounds` / `stock_inbound_items` 扩展字段 | 表头结算归属；明细供应商归属状态、供应商补录信息、应付来源关系和结算备注；不保存员工报销关联 |
| `employee_expenses`（后续） | 独立员工采购/费用报销数据；当前仅做前端，不建立后端实体，不关联采购入库 |
| `purchase_invoices` / `purchase_invoice_allocations`（建议） | 发票基础资料、发票金额/税额、附件、供应商及发票到采购订单/入库批次/应付流水的分配关系 |
| `supplier_reconciliations` | 供应商、期间、账务快照、对方确认金额、差异原因、确认人和确认时间；第三阶段已实现 |
| `supplier_refunds` | 供应商退款申请、退款金额、银行入账账户、退款状态和对应贷项；第三阶段已实现 |

建议账务类型包括 `INITIAL`、`PURCHASE_INBOUND`、`INDEPENDENT_PURCHASE_INBOUND`、`PURCHASE_RETURN`、`PAYMENT`、`ADVANCE_PAYMENT`、`CREDIT`、`CREDIT_ALLOCATION`、`ADJUSTMENT` 及对应冲销类型。发票登记不新增供应商应付账务类型，只更新应付来源的开票状态和发票分配关系。员工采购/费用报销第一阶段不产生后端账务流水。原始账务流水不得直接覆盖，反审核必须新增冲销流水并通过 `reversalOfId` 关联原流水。业务审核应在单一数据库事务中完成，且要有来源类型、来源 ID、来源明细 ID 和幂等键唯一约束，避免重复审核造成重复入账。

建议分别存储和展示：

```text
应付余额 = 期初应付 + 已审核采购入账 + 应付费用 + 应付调整 - 已审核退货 - 已分配付款
供应商预付款余额 = 期初预付款 + 付款超出核销金额的部分 - 已核销预付款
供应商贷项余额 = 已付款退货形成的贷项 + 其他贷项调整 - 已核销贷项
```

三种余额必须分别显示；如需展示净结算额，应使用“应付余额 - 预付款余额 - 贷项余额”，同时保留上述分项，不应只返回一个可能为负数的 `payable`。

## 9. 验收场景

1. 采购 1,000 件，分两批审核入库 500 + 500：采购进度先为 50%，后为 100%；第一批审核只确认第一批应付。
2. 第一批应付 5,000 元，付款 2,000 元：采购进度仍为 50%，付款显示部分付款，未付应付为 3,000 元。
3. 第二批入库完成后：采购履约变为完成，但付款状态仍按实际已付款和应付计算，不自动变为已结清。
4. 采购数量 1,000，实际审核入库 1,100：库存和应付按 1,100 计算，采购履约显示已完成/超收 100，不再提供补充入库。
5. 退回已入库商品：可退数量受历史有效退货限制，审核后库存按原入库成本减少，供应商账务按实际确认退货金额出现对应贷项。
6. 对已付款货物发起退货：采购退货形成供应商贷项；如实际收到供应商退款，再通过独立退款单登记银行入账。
7. 正常独立入库不选择供应商，审核后只增加库存并显示“已入库/无需结算”。
8. 待补供应商入库审核后只增加库存，显示“已入库/待补供应商”，不生成应付。
9. 为待补供应商入库补录多个明细供应商并确认应付后，按供应商和入库明细分别生成应付流水，不重复增加库存，也不生成采购订单。
10. 员工采购/费用报销前端只展示临时原型数据，不关联采购入库、库存、供应商或供应商应付。
11. 一个采购订单多个商品、多个供应商：入库、退货、付款和对账金额都归到对应商品行供应商。
12. 草稿保存不影响库存、银行余额和供应商账务；审核重复提交不得重复入账；反审核后库存和账务流水可追溯恢复。
13. 入库审核产生应付后，开票状态默认为“未开票”；采购订单和供应商对账单可以筛选未开票应付。
14. 一张发票可以分配多张入库单，同一张入库单可以分多张发票；登记发票不重复生成应付、不改变库存和银行余额。
15. 部分开票显示“部分开票”，发票金额或税额不一致显示“开票有差异”，不能直接覆盖原应付金额。
16. 采购退货允许录入供应商实际确认金额；库存按原入库价格减少，供应商应付按确认金额冲减，差额生成独立调整记录。
17. 采购退货价格差异必须填写原因和确认信息，不能覆盖原入库单价或历史采购金额。
18. 采购退货后采购订单累计入库数量和履约状态保持不变；已完成订单不重新出现补充入库，需补货时创建新单据。
19. 供应商付款单保存草稿时不改变余额；审核后才减少银行余额、增加付款流水并核销供应商应付。
20. 一张付款单可以核销多条应付，一条应付可以被多张付款单部分核销；核销金额不能超过未核销余额。
21. 付款金额大于核销金额时，差额明确记录为供应商预付款；付款金额小于核销金额时不得审核；预付款和贷项分别核销。
22. 供应商对账单按期间展示的期初 + 期间发生额 = 期末，并可追溯每笔来源单据。
23. 未明确供应商或商品明细归属的采购费用不能进入应付或库存成本；已归属费用按未税金额、税额和含税金额分别展示。
24. 采购入库和应付确认支持同一单据多个供应商，重复审核、重复补录和重复确认都必须幂等。
25. 第一阶段员工费用页面刷新后不保证数据保留，不显示真实审核、付款或余额结果。

## 10. 建议实施顺序

### 第一阶段：采购履约、应付基础与内部对账

- 明确采购履约状态与付款状态分开。
- 在独立采购入库中增加结算归属，正常独立入库不选择供应商，仅支持待补供应商例外。
- 将供应商归属、应付来源和应付确认状态下沉到入库明细，支持同一入库单多个供应商。
- 建立新的供应商账务流水，并支持按新规则录入可选期初余额；不迁移旧 `suppliers.payable`。
- 采购订单入库审核/反审核与应付流水联动；独立入库只支持无需结算和待补供应商状态。
- 采购订单列表显示采购履约进度、开票状态和付款状态；移除或明确标记不再代表真实付款的订单“本次付款”字段。
- 提供供应商应付汇总、内部对账明细、打印和导出；分别展示应付、预付款和贷项。
- 第一阶段只增加基础开票状态和开票备注，不开发完整发票分配接口。
- 增加员工采购/费用报销前端原型，使用临时页面状态，不建立后端实体。

### 第二阶段：供应商付款与发票登记

- 新增供应商付款单，复用客户收款单的草稿、核销、审核、反审核模式。
- 新增付款核销选择组件，支持部分付款、多条应付分配、预付款和贷项核销。
- 实现供应商付款单与银行账户、供应商应付流水联动。
- 增加待补供应商处理页，支持补录供应商和确认应付。
- 增加采购发票登记，支持部分开票、发票分配和开票差异。
- 增加“无票付款”财务规则；若启用见票付款，付款审核必须校验开票状态。

### 第三阶段：采购退货及正式对账（已完成）

- 已新增采购退货列表和表单；退货来源限定为已确认应付的原材料入库批次，并按原批次、成本和现存库存校验可退数量。
- 退货审核/反审核联动库存流水、供应商应付、贷项及差异调整；不回减采购订单累计入库数量。

- 已新增带账务快照的正式对账确认；确认前校验快照未变化，确认后锁定供应商/门店对账期间。

## 11. 待确认事项

开始开发前建议先确认以下规则：

1. **应付确认时点（建议采用）**：第一阶段按关联采购入库审核确认应付；发票只作为独立的开票状态和核对记录，不重复生成应付。
2. **采购费用与员工报销边界（已确认）**：供应商采购费用第一阶段不做自动分摊，必须明确归属供应商/商品明细；员工垫付、办公用品、五金和零星采购独立放在财务/员工前端模块，不与原材料采购挂钩。
3. **采购退货金额（已确认采用差异金额）**：允许录入供应商实际确认的退货金额；库存按原入库价格快照减少，供应商应付按确认金额冲减，差额作为独立采购退货价格调整并记录原因。
4. **采购退货后的履约数量（已确认）**：退货只冲减库存和应付，不回减采购订单累计入库数量，也不改变原采购订单履约状态；需要补货时创建新的采购订单或独立采购入库。
5. **超额付款（已确认允许）**：允许超过当前应付付款，超出部分形成供应商预付款，并与应付余额分开显示、后续支持核销。
6. **对账范围（已确认并实现）**：内部对账持续提供查询、打印和导出；正式供应商确认使用独立快照单据，并在确认后锁定所选期间。
7. **历史余额（已确认不迁移）**：开发端不迁移旧 `suppliers.payable`，不做旧数据兼容，直接使用新的供应商账务流水；如有需要，只按新规则重新录入期初余额。
8. **独立入库审核规则（已确认允许）**：`pending_supplier` 独立入库允许先审核库存；必须显示“待补供应商”，且不产生应付。`none` 独立入库显示“无需结算”。
9. **报销模块范围（已确认）**：第一阶段只做独立的员工采购/费用报销前端页面和交互，不与独立入库、采购订单、库存或供应商应付关联；正式报销审核和付款后续单独设计。
10. **无票付款规则（已确认允许）**：允许供应商未开票时付款，但必须填写未开票付款原因；第一阶段 `paymentRequireInvoice` 默认关闭，后续如需见票付款再开启。
11. **预付款规则（已确认）**：付款金额超过本次核销金额时自动形成供应商预付款，必须单独展示并支持后续核销。
12. **独立入库供应商规则（建议确认）**：正常独立入库不选择供应商；明确供应商的原材料采购必须关联采购订单。只有待补供应商例外允许先审核库存，后续由财务补录供应商并确认应付。
13. **多供应商入库规则（建议确认）**：供应商归属、供应商补录状态和应付来源按入库明细保存；同一入库单可以包含多个供应商。
14. **供应商退款规则（已确认并实现）**：采购退货与银行退款分开建单；退货先形成应付冲减/贷项，实际退款必须关联有效贷项并通过退款单审核入账。
15. **员工费用持久化规则（已确认第一阶段不做后端）**：员工采购/费用报销页面只作为前端原型，刷新后不保证保留数据，不展示真实审核和付款结果。

上述规则确认后，再据此更新 API 接口文档、README 路由/组件说明和权限目录，并进入代码实现。

## 12. 本次实现状态（2026-10-07）

第一阶段已在当前代码库落地：

- 采购履约按已审核入库统计，进度展示封顶 100%，保留超收数量；混合单位按已完成明细行数统计。
- 采购订单审核只形成采购承诺；关联入库审核按实际数量、明细供应商、单价和税额快照生成新账务应付。
- 独立入库支持 `none` 和 `pending_supplier`；待补供应商入库先审核库存，再按明细补录供应商并确认应付，不重复增加库存。待补处理入口提前落地，形成第一阶段闭环。
- 新增供应商应付/预付款/贷项、内部对账、期初余额、基础开票状态和采购费用明确归属页面及接口。
- 新账务只使用 `supplier_account_transactions`，不迁移、不读取、不写入旧 `suppliers.payable`；首次数据库访问自动创建新表和必要字段，不追溯生成历史已审核入库应付。
- 关键业务操作加入门店/仓库范围、版本校验和幂等处理；员工费用仍为纯前端临时原型。

第二阶段已落地供应商付款草稿/审核/反审核、部分及多来源核销、超额付款预付款、独立预付款/贷项核销、银行流水、采购发票登记/部分分配/差异/确认撤销，以及见票付款和无票付款豁免规则。详情支持来源与银行流水追溯，财务附件按登录和门店私有下载，新权限分类使用中文名称。
